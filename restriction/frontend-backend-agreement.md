# 珞珈烟火邮局前后端协作协议

## 1. 文档信息

1. 协议版本：`0.2.2`。
2. 制定日期：`2026-10-16`。
3. 当前状态：MVP 开发约定。
4. 适用项目：珞珈烟火邮局 Web 端与 FastAPI 后端。
5. 机器可读接口契约：[`openapi.yaml`](./openapi.yaml)。
6. 当本文与 OpenAPI 对字段、路径或状态码的描述不一致时，以 `openapi.yaml` 为准，并立即修正文档。

## 2. 已确定的技术方案

1. 前端通过 HTTP JSON API 与后端通信。
2. 后端使用 FastAPI。
3. 数据库使用 MySQL 8.x。
4. ORM 使用 SQLAlchemy 2.x。
5. 数据库迁移使用 Alembic。
6. 数据模型与请求校验使用 Pydantic v2。
7. MVP 默认使用同步 SQLAlchemy Session 与 PyMySQL。
8. 访问数据库的 FastAPI 路由使用普通 `def`，禁止在 `async def` 中直接执行同步数据库操作。
9. 后续如果整体切换到异步方案，必须同时切换为 `AsyncSession` 和异步 MySQL Driver，不允许同步、异步 Session 混用。

## 3. 单一事实来源

1. `restriction/openapi.yaml` 是接口路径、请求字段、响应字段、枚举和状态码的唯一事实来源。
2. FastAPI 自动生成的 OpenAPI 必须与该文件保持语义一致。
3. 前端 Mock Data 必须根据该文件生成或手动维护。
4. 后端修改接口前，必须先修改 OpenAPI 并通知前端。
5. 前端不得依赖 OpenAPI 中未声明的字段。
6. 后端不得无通知地删除字段、修改字段类型或改变枚举含义。

## 4. 服务地址

1. 生产环境优先使用同源部署：

```text
/api/v1
```

2. FastAPI 本地开发地址：

```text
http://127.0.0.1:8000/api/v1
```

3. 前端代码不得在业务组件中硬编码完整后端地址。
4. 前端通过环境变量配置 API Base URL。
5. API 主版本固定包含在 URL 中。
6. 不兼容修改必须发布新的主版本，例如 `/api/v2`。

## 5. 请求格式

1. 默认请求和响应编码为 UTF-8。
2. 默认请求类型为：

```http
Content-Type: application/json
Accept: application/json
```

3. JSON 字段统一使用 `lowerCamelCase`。
4. URL 路径资源名使用英文小写复数。
5. URL 不使用尾部 `/`。
6. 资源 ID 始终使用字符串。
7. 布尔值必须使用 JSON `true` 或 `false`。
8. 缺失字段和显式 `null` 含义不同，前端不得随意互换。
9. 前端不得提交 OpenAPI 未声明的字段。
10. 后端 Pydantic 请求模型默认设置 `extra="forbid"`。

## 6. 时间约定

1. MySQL 中的业务时间统一保存为 UTC。
2. 数据库时间字段使用 `DATETIME(6)`。
3. API 使用带时区的 ISO 8601/RFC 3339 字符串。
4. 推荐的 API 时间形式：

```text
2026-10-16T08:30:00Z
```

5. 前端负责将时间转换为用户所在时区展示。
6. 前端不得把本地格式化后的中文日期传回后端。
7. 前端提交的任何业务时间都必须包含时区，后端收到后转换为 UTC。

## 7. 成功响应

1. 所有带响应体的成功请求使用统一结构：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "requestId": "req_01JABCD2EFGH3456789"
}
```

2. `code` 为 `0` 表示业务成功。
3. `data` 的具体结构由对应 OpenAPI Schema 决定。
4. 无业务数据的成功响应仍返回 JSON：

```json
{
  "code": 0,
  "message": "success",
  "data": null,
  "requestId": "req_01JABCD2EFGH3456789"
}
```

5. MVP 不使用空响应体的 `204 No Content`。
6. 创建成功使用 HTTP `201`。
7. 查询、修改、删除和幂等操作成功通常使用 HTTP `200`。

## 8. 失败响应

1. 所有失败请求使用统一结构：

```json
{
  "code": 42201,
  "message": "信件内容未通过校验",
  "data": {
    "fieldErrors": {
      "content": "正文长度必须为 20 至 1500 个字符"
    }
  },
  "requestId": "req_01JABCD2EFGH3456789"
}
```

2. 前端使用 `code` 判断具体业务错误。
3. 前端不得依赖 `message` 文本判断逻辑。
4. `message` 是可直接展示给用户的简短中文信息。
5. 后端不得在响应中暴露 SQL、调用栈、文件路径、密码或环境变量。
6. HTTP 状态码与错误码范围约定如下：

| HTTP | 业务码范围 | 含义 |
|---|---:|---|
| 400 | 40000–40099 | 请求格式或查询参数错误 |
| 401 | 40100–40199 | 未登录、登录失效或凭据错误 |
| 403 | 40300–40399 | 权限不足或 CSRF 校验失败 |
| 404 | 40400–40499 | 资源不存在或当前用户不可见 |
| 409 | 40900–40999 | 重复请求、唯一键或状态冲突 |
| 422 | 42200–42299 | 业务字段校验或内容安全失败 |
| 429 | 42900–42999 | 请求频率超限 |
| 500 | 50000–59999 | 后端内部错误 |

7. FastAPI 默认的 `RequestValidationError` 必须被自定义异常处理器转换为上述结构。
8. SQLAlchemy 的完整性约束异常必须转换为稳定的 `409xx` 业务错误。
9. 所有响应体必须包含 `requestId`。
10. 后端同时在响应头返回 `X-Request-Id`。

## 9. 登录与 Session

1. Web 端使用服务端 Session，不在浏览器存储 JWT。
2. Session Cookie 名称为：

```text
luojia_session
```

3. 生产环境 Cookie 属性必须为：

```text
HttpOnly=true
Secure=true
SameSite=Lax
Path=/
```

4. 本地 HTTP 开发环境允许临时设置 `Secure=false`。
5. 前端请求必须启用凭据：

```js
fetch(url, {
  credentials: "include"
});
```

6. 普通用户可以通过 `POST /auth/register` 自行注册。
7. 注册接口只能创建 `role=user` 的账户，前端不得提交角色字段。
8. 用户名统一转为小写保存，格式为 3–32 位小写字母、数字或下划线。
9. 用户可以通过 `PATCH /me/profile` 修改用户名；修改时必须提交当前密码，由后端检查密码和唯一性。
10. 登录或注册成功后，后端通过 `Set-Cookie` 设置 Session。
11. 登录或注册响应中的 CSRF Token 只保存在前端内存状态中。
12. CSRF Token 不写入 `localStorage` 或 `sessionStorage`。
13. 所有登录态写操作必须携带：

```http
X-CSRF-Token: <token>
```

14. 读取接口不要求 CSRF Token。
15. 收到 HTTP `401` 时，前端清空本地用户状态并引导重新登录。
16. 收到 HTTP `403` 时，前端提示权限不足，不自动重新登录。
17. 用户选择匿名发布时，后端仍保存真实 `userId`，匿名只影响公开展示。
18. 前端永远不能接触 MySQL 用户名、密码或连接地址。

## 10. CORS 约定

1. 生产环境优先同源，不启用宽泛 CORS。
2. 开发环境允许的 Origin 由后端环境变量明确配置。
3. 本地 Origin 示例：

```text
http://127.0.0.1:4173
http://localhost:4173
```

4. 携带 Cookie 时禁止返回：

```http
Access-Control-Allow-Origin: *
```

5. 后端必须设置 `allow_credentials=true`。
6. 允许的 Method 和 Header 使用白名单，不使用无条件全开放配置。

## 11. 分页、筛选与排序

1. 页码从 `1` 开始。
2. 默认 `pageSize` 为 `20`。
3. 最大 `pageSize` 为 `50`。
4. 统一分页结构：

```json
{
  "items": [],
  "page": 1,
  "pageSize": 20,
  "total": 0,
  "hasMore": false
}
```

5. 列表查询必须使用稳定排序。
6. 按发布时间倒序的实际排序规则为：

```text
published_at DESC, id DESC
```

7. 相同参数的重复 GET 请求必须保持字段结构一致。
8. 搜索关键字最大长度为 50 个字符。
9. 空搜索关键字按未提供处理。
10. 前端切换筛选条件时将页码重置为 `1`。

## 12. 幂等和重复提交

1. 创建信件、创建完整回信和创建简短回应必须携带 `Idempotency-Key`。
2. 推荐使用 UUID 作为 Key。
3. Key 长度为 16 至 128 个字符。
4. 后端按“用户、路由、Key”保存请求摘要和执行结果。
5. 相同 Key 和相同请求体在 24 小时内返回首次执行结果。
6. 相同 Key 配合不同请求体返回 HTTP `409`。
7. 收藏、取消收藏、共鸣和取消共鸣接口本身是幂等接口。
8. 前端提交期间必须禁用重复提交按钮。
9. 网络超时后，前端重试创建请求时必须复用原 Key。

## 13. 信件字段限制

1. 标题长度为 2 至 80 个 Unicode 字符。
2. 正文长度为 20 至 1500 个 Unicode 字符。
3. 地点只能使用 `/metadata` 返回的预设 `locationId`，允许不选择地点。
4. 正文格式为纯文本。
5. 换行使用 `\n`。
6. 前端不得向正文中插入 HTML。
7. 后端必须对所有文本执行内容安全和输出转义处理。
8. `isAnonymous` 必须为布尔值，匿名时数据库仍保存真实 `userId`。
9. 支持最多 30 个字符的可选笔名 `penName`。
10. 收信目标 `recipientType` 只能为：

```text
wall
user
```

11. `recipientType=wall` 表示投递到信墙，数据库可见范围为 `public`，提交后由管理员审核。
12. `recipientType=user` 时必须提供 `recipientUserId`，数据库可见范围为 `private`；创建后初始仅发送者和接收者可读，不进入审核。
13. 首版不支持定时寄信，不接收 `scheduledAt`。
14. 初版不提供标签功能，前端不得提交 `tagIds`。
15. 信纸图案必须使用 `/metadata` 返回的有效 `patternId`。
16. 地点和信纸的名称、视觉资源与展示顺序由前端/视觉设计提出。
17. 后端负责稳定 ID、seed 数据、启停状态、引用校验和 `/metadata` 输出。
18. 前端不得把展示名称当作数据库 ID，也不得在请求中临时创造选项。
19. 初版信纸资源为 `niupi.png`、`rice-yellow.png` 和 `white.png`，统一放在 `pictures/material/letter-paper`。
20. `saveAsDraft=true` 时保存为草稿，不提交管理员审核。
21. 信件状态只能为：

```text
draft
active
deleted
```

22. 可见范围与状态分开存储，可见范围只能为：

```text
private
public
```

23. 审核过程不使用 `pending`、`rejected`、`hidden` 或 `withdrawn` 状态。
24. 等待审核通过以下条件表达：`status=active`、`visibility=public`、`submittedAt` 非空、`publishedAt` 为空。
25. 审核通过后填写 `publishedAt`。
26. 管理员退回修改时，信件恢复为 `draft`，退回原因写入审核记录。
27. 作者撤下公开信件时改为 `draft` 并清空 `publishedAt`，不使用 `withdrawn` 状态。
28. 管理员移除违规内容时改为 `deleted`，不使用 `hidden` 状态。

## 14. 简短回应与完整回信

1. 简短回应和完整回信分开建模。
2. 简短回应正文长度为 2 至 300 个 Unicode 字符。
3. 简短回应为纯文本，存入 `responses` 表。
4. 简短回应支持笔名和匿名。
5. 公开简短回应必须由管理员审核后才能展示。
6. 简短回应的审核过程同样使用 `submittedAt` 和 `publishedAt`，不使用 `pending` 或 `rejected` 状态。
7. 完整回信是新的 `letters` 记录，通过 `parentLetterId` 关联原信。
8. 首版只允许一层关联；已经存在 `parentLetterId` 的信件不能继续作为完整回信的原信。
9. 写给信墙的完整回信属于公开信件，需要管理员审核。
10. 写给某个用户的完整回信属于私人信件，不进入审核。
11. 原信关闭 `allowResponses` 后不能新增简短回应。
12. 原信关闭 `allowReplies` 后不能新增完整回信。
13. 已删除或尚未公开的信墙信件不能接收公开互动。
14. 私人信件允许通过 `POST /letters/{letterId}/forward` 转发给某个用户。
15. 转发只建立读取授权，不复制信件正文，也不会把私人信件改成公开信件。
16. 原发送者、原接收者和有效转发接收者可以继续转发；最终权限仍由后端判断。
17. 原信删除后，所有转发访问立即失效。

## 15. 状态与权限

1. 系统角色只有 `user` 和 `admin`。
2. “作者”是资源所有权关系，不是账户角色。
3. 未登录用户可以浏览已经填写 `publishedAt` 的公开信件、简短回应、故事和企划。
4. 登录用户可以写信、完整回信、简短回应、共鸣、收藏和查看自己的内容。
5. 私人信件只允许发送者、原接收者和有效转发接收者读取。
6. 普通用户只能编辑自己的信件，不能编辑收到或经转发获得的私人信件。
7. 修改已公开信件时，后端立即清空 `publishedAt`，旧版本同步停止展示；修改后的内容必须重新提交审核。
8. 普通用户不能直接填写 `publishedAt` 或审核记录。
9. 只有 `admin` 可以审核公开信件、公开完整回信和简短回应。
10. 管理员可以执行通过、退回修改和删除操作。
11. 管理员默认不能读取私人信件正文。
12. MVP 不提供管理员读取私人信件的接口；未来如增加安全事件访问，必须单独授权并写入不可修改的审计记录。
13. 管理员权限必须由后端判断。
14. 前端隐藏按钮不等于权限校验。
15. 对无权查看的私人资源，后端返回 `404`，避免泄露资源是否存在。

## 16. 前端处理要求

1. 前端必须对加载中、空数据、失败和成功状态分别展示。
2. 前端收到未知字段时可以忽略，但不能依赖未知字段。
3. 前端收到未知枚举值时展示兜底状态并记录日志。
4. 前端不得直接展示后端返回的未清洗 HTML。
5. 前端不得自行计算权限并绕过后端结果。
6. 写操作失败后保留用户尚未提交的文本。
7. 网络错误和业务错误使用不同提示。
8. HTTP `429` 时读取 `Retry-After`，倒计时结束前禁止连续请求。
9. HTTP `500` 时展示通用错误和 `requestId`，不得展示后端内部信息。
10. 前端埋点和日志不得记录密码、Cookie、CSRF Token 或完整信件私密正文。

## 17. FastAPI 后端要求

1. 每个路由必须声明 `response_model`。
2. ORM 实体不得直接作为公开响应返回。
3. Pydantic 响应模型只包含 OpenAPI 声明的字段。
4. 请求模型禁止额外字段。
5. 数据库 Session 通过依赖注入获取并确保关闭。
6. 业务层控制事务提交和回滚。
7. 路由层不零散调用 `commit()`。
8. 后端必须统一处理以下异常：

   - Pydantic/FastAPI 请求校验异常。
   - 登录与权限异常。
   - SQLAlchemy 唯一键和外键异常。
   - 数据库连接异常。
   - 未捕获异常。

9. 日志使用结构化格式并包含 `requestId`。
10. 日志不得记录密码、Session、CSRF Token 或数据库连接密码。
11. `/docs` 和 `/openapi.json` 在开发环境开启。
12. 生产环境是否公开接口文档由部署配置决定。

## 18. MySQL 约束

1. 应用使用独立数据库账户 `luojia_app`。
2. 应用禁止使用 MySQL root 账户运行。
3. 数据库名称为：

```text
luojia_post_office
```

4. 存储引擎统一为 `InnoDB`。
5. 字符集统一为 `utf8mb4`。
6. 默认排序规则统一为 `utf8mb4_0900_ai_ci`。
7. 表名和列名统一使用 `snake_case`。
8. 主键 ID 对外使用带资源前缀的字符串 ULID，例如：

```text
usr_01J...
let_01J...
res_01J...
```

9. 业务表至少包含：

```text
id
created_at
updated_at
deleted_at
version
```

10. 删除业务内容默认使用软删除，软删除后立即不可访问。
11. 软删除数据保留 15 天，期满后由后端定时任务物理清理业务正文。
12. 审核与必要安全审计记录可以继续保留，但不得保留完整私人信件正文。
13. 状态字段使用 `VARCHAR`，不使用 MySQL `ENUM`。
14. 收藏表必须设置唯一约束：

```text
UNIQUE(user_id, letter_id)
```

15. 必须为外键、审核队列和列表排序建立索引。
16. 信件正文可以使用 `TEXT`，但后端仍必须执行 1500 字符业务限制。
17. 字符长度按 Unicode 字符计算，不按 UTF-8 字节数计算。

## 19. 数据库迁移

1. 所有数据库结构变更使用 Alembic。
2. 生产环境禁止通过 SQLAlchemy `create_all()` 自动变更表结构。
3. 每次 Model 变更必须同时提交 migration。
4. migration 文件进入 Git 管理。
5. migration 必须在空数据库上验证升级成功。
6. migration 必须在包含旧数据的测试数据库上验证升级成功。
7. ORM Model、Pydantic Schema、OpenAPI 和 migration 必须在同一个功能变更中同步更新。

## 20. 配置与密钥

1. 真实配置保存在 `.env`。
2. `.env` 必须加入 `.gitignore`。
3. 仓库只提交不含真实秘密的 `.env.example`。
4. 后端数据库连接示例：

```text
DATABASE_URL=mysql+pymysql://luojia_app:<password>@127.0.0.1:3306/luojia_post_office?charset=utf8mb4
```

5. 密码中的特殊字符必须进行 URL 编码。
6. 数据库密码不得发给前端同学。
7. 数据库密码不得出现在截图、日志、报错或 Git 历史中。

## 21. 接口变更流程

1. 提出接口变更时先修改 `openapi.yaml`。
2. 变更说明必须包含原因、影响接口和兼容性。
3. 新增可选字段属于兼容性变更。
4. 删除字段、修改类型、修改语义或收紧必填条件属于不兼容变更。
5. 不兼容变更必须获得前后端双方确认。
6. 不兼容变更原则上发布新的 API 主版本。
7. 前端完成适配前，后端不得提前移除旧字段。
8. 联调中发现文档错误时，先修正文档再修代码。

## 22. 联调验收清单

1. OpenAPI YAML 可以正常解析。
2. 所有 `$ref` 均能解析。
3. FastAPI `/openapi.json` 与约定语义一致。
4. 首页聚合接口能够返回统计数据。
5. 注册、登录、当前用户、用户名修改和退出登录流程可用。
6. Cookie 与 CSRF 防护生效。
7. 信件列表、详情、创建、收件箱、编辑和删除流程可用。
8. 回信列表、创建和私人信件转发流程可用。
9. 收藏和取消收藏保持幂等。
10. 修改已公开信件后，旧版本立即停止展示。
11. 中文、Emoji、换行和长度边界测试通过。
12. `401`、`403`、`404`、`409`、`422`、`429` 和 `500` 格式统一。
13. 所有失败响应都能通过 `requestId` 定位日志。
14. 前端不包含任何数据库凭据。
15. MySQL migration 可以在新数据库中完整执行。

## 23. MVP 开发顺序

1. 后端建立 FastAPI 项目结构和统一异常响应。
2. 后端配置 SQLAlchemy、PyMySQL 和 Alembic。
3. 后端完成用户注册、资料修改、Session 和 CSRF。
4. 后端完成信件列表、详情和创建接口。
5. 前端用 OpenAPI Mock Data 完成页面交互。
6. 前后端联调注册、登录、信件、转发和回信流程。
7. 后端完成收藏、个人中心和审核接口。
8. 最后接入首页真实统计数据、故事和特别企划。
